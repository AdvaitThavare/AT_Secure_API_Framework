# AT Secure API Framework

A TypeScript-based API security testing framework for building and testing secure API flows using **HTTPS/mTLS** and multiple application-level encryption strategies.

## Current Status

The framework currently supports:

* HTTPS with mutual TLS (mTLS)
* Request/response payload processing
* Payload and encryption-type routing
* Request validation and normalization
* JWE
* AES_RSA
* JWS_AES_RSA
* Common error handling
* Local HTTPS echo-service testing
* Postman interoperability testing

---

## Architecture

The current request/response flow is:

```text
Client / Postman
       |
       | HTTPS + mTLS
       v
HTTP Server
       |
       v
Request Identification
       |
       v
Validation / Normalization
       |
       v
Cryptography
       |
       v
Service
       |
       v
Cryptography
       |
       v
HTTP Response
```

Cryptography is routed through a common strategy layer:

```text
Encryption Type
      |
      v
Crypto Strategy
      |
      +--> decrypt()
      |
      +--> encrypt()
```

## Supported Encryption Types

### JWE

```text
RSA-OAEP-256
      +
AES-256-GCM
```

Provides authenticated encryption through AES-GCM.

### AES_RSA

```text
Plaintext
    |
AES-256-CBC
    |
Encrypted Payload

AES Key
    |
RSA/PKCS#1 v1.5
    |
Encrypted Key
```

Configuration:

* AES-256-CBC
* PKCS#7 padding
* 16-byte IV
* RSA/PKCS#1 v1.5
* No signature

The absence of a signature is intentional for this protocol.

### JWS_AES_RSA

```text
Plaintext
    |
RS256 JWS
    |
Signed Plaintext
    |
AES-256-CBC
    |
Encrypted Payload

AES Key
    |
RSA/PKCS#1 v1.5
    |
Encrypted Key
```

Configuration:

* RS256
* AES-256-CBC
* PKCS#7 padding
* 16-byte IV
* RSA/PKCS#1 v1.5

## Encrypted Request Format

AES_RSA and JWS_AES_RSA requests use a normalized encrypted wrapper.

External representation:

```json
{
  "encReqPayload": "...",
  "encReqKey": "..."
}
```

The request-normalization layer converts the external representation into the internal format used by cryptography strategies.

JWE does not require an encrypted AES key.

---

## Encrypted Response Format

AES_RSA and JWS_AES_RSA responses use:

```json
{
  "encResPayload": "...",
  "encResKey": "..."
}
```

The response structure is generated by the corresponding cryptography strategy.

## mTLS

The local development environment uses mutual TLS:

```text
Local CA
   |
   +--> Server Certificate
   |
   +--> Client Certificate
```

The server requires the appropriate certificates/keys for establishing the mTLS connection.

Where required by the protocol, the same certificate/key material may also be used for application-level cryptographic operations.

## Security Notes

This project is intended primarily for **API security development, testing, and interoperability validation**.

Important protocol characteristics:

* AES_RSA intentionally provides encryption without a JWS signature.
* JWS_AES_RSA signs the plaintext before AES encryption.
* JWE uses authenticated encryption.
* AES-CBC currently uses a fixed IV as required by the current test/protocol implementation.
* Dynamic IV handling is a planned protocol/design discussion and should not be introduced without defining how the IV is transported to the decrypting party.
* `ignoreHTTPSErrors` or equivalent development-only TLS bypasses should not be treated as production configuration.
